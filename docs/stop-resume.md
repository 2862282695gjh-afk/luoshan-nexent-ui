# 停止生成后继续对话

2026-09-28。页面的停止交互已对齐 Nexent 原生聊天页：先中断浏览器侧 SSE，再异步通知服务端停止；同一会话 ID 可立刻用于下一轮。当前 v2.5.1 运行服务仍有一个启动阶段的停止竞态，见下文；它需要后端修复，前端不能可靠绕过。

## 页面行为

- 每次发送都有独立的 `ChatRun`，包含浏览器 `AbortController`、回复消息对象和本轮 `conversation_id`。
- 用户点击停止后，页面立刻将该回复标为“已停止”、中断旧 SSE 读取，并在后台调用 `GET /nb/v1/chat/stop/{conversation_id}`。不等待旧流 EOF。
- 输入框和发送按钮随即恢复；下一轮仍携带原会话 ID。旧流的迟到事件、超时、异常和 `finally` 只能处理旧回复，不能把新一轮错误标成“提前中断”或清掉新一轮的流式状态。
- 如果停止前尚未收到会话 ID，页面只能停止本地读取，并提示服务端状态未知；不会凭空请求停止其他会话。
- 停止请求失败时，已经停止本地读取，页面以提示告知服务端未确认。不会自动重发用户问题。
- 服务端若以 SSE `error` 返回“当前会话已有智能体任务正在运行”或 `Rejected concurrent agent run`，页面会明确提示上一轮尚未在服务端生效，而不把它误报成普通连接中断。

PC 和移动端使用同一套时序。浏览器回归覆盖：已知/未知会话 ID 停止、停止接口 503、旧流延迟收尾、新轮复用同一 ID，以及旧轮不影响新轮。

## 实际后端复现

使用当前 Docker 的 Nexent v2.5.1 / `43c227c70` 运行服务进行了真实测试：首轮开始后立即停止、关闭旧浏览器读取、再使用相同 `conversation_id` 发送第二轮。第二轮 HTTP 仍为 200，但只收到一个 SSE `error`，没有 `final_answer`。

服务日志的顺序如下：

```text
08:08:58.403  stop 成功
08:08:58.484  首轮 register agent run
08:08:58.488  第二轮 Rejected concurrent agent run
08:09:07.620  首轮 unregister
```

因此，停止接口的 HTTP 200 只表示请求被接收，不代表会话运行槽位已经释放。页面按原生 Nexent 前端方式处理后，仍会撞到这个服务端竞态；不是前端 SSE 分帧或“Code execution failed”提示导致的续聊失败。

## 根因与后端修复方向

以下行号来自运行容器 `/opt/backend`。本机工作副本是不同且有未提交修改的 v2.4 基线，不能直接替换运行镜像。

| 运行容器代码位置                           | 当前行为                                                     |
| ------------------------------------------ | ------------------------------------------------------------ |
| `services/agent_service.py:3697`           | 先为 `(user_id, conversation_id)` 创建 `_reservations`。     |
| `services/agent_service.py:3039`           | 异步准备完成后才注册真实 `AgentRunInfo`。                    |
| `agents/agent_run_manager.py:134`          | 停止落在预备窗口时找不到已注册运行，只写取消标记后返回成功。 |
| `services/runtime_state_service.py:94-110` | 后续注册无条件删除取消标记。                                 |
| `services/agent_service.py:3701`           | 第二轮发现首轮 reservation 尚在，返回单个 SSE `error`。      |

最小可用修复应将 reservation 也作为可停止的运行句柄：它需要本轮 token、取消状态和完成信号；停止请求在同一锁内标记目标 reservation；准备和注册前再次校验 token；已取消的准备按“已停止”收尾、释放 reservation 和旧流通道。停止接口应有界等待目标 reservation/run 真正退出后，再确认可续聊。

不要只删除 `register_run()` 中清理取消标记的代码，也不要停止时直接删除 reservation：前者会把旧轮取消误伤新轮，后者会使旧 producer 与新轮共用会话资源。多 runtime 实例部署还需要把 token 纳入 Redis 的 lease/cancel 状态；仅以用户和会话构成的取消 key 无法区分新旧轮次。

后端验收至少应包含：

- reservation 阶段停止后不启动模型，且不会残留会话占用；
- stop 成功返回后，同一 `conversation_id` 的下一轮能产生终态答案；
- 已注册运行的停止仍可正常工作；
- 无活动运行的 stop 不会误伤下一轮；
- 多实例下旧轮的停止和延迟清理不影响新 token。

在后端补丁部署前，若页面显示“上一轮停止尚未在服务端生效”，应等待服务端释放后重发，或新建对话临时继续。前端不会清 Redis、伪造完成状态或自动重发，避免造成重复执行。
